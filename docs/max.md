# Ben's Polyphonic Pitch Shifter in Max and Max for Live

Two things are offered for Max users: a compiled object, `polypitch~`, and a Max for Live audio effect built on
it. Both run the same code as the plug-in (`engine/PolyPitchProcessor.h`), so sound, latency and CPU are the same.

**Status: built, not yet run inside Max.** The object compiles as a universal binary and exports its entry point;
the code it wraps is the code the plug-in runs, which is tested. The check described at the end of this page has
not been run yet.

## The package

`max/PolyPitch/` is a Max package:

```
max/PolyPitch/
  package-info.json
  externals/polypitch~.mxo          built by scripts/build.sh max (not in git)
  help/polypitch~.maxhelp
  source/projects/polypitch_tilde/  the object's source and build file
```

Install it with `scripts/install-macos.sh max`, which copies the package into `~/Documents/Max 9/Packages`
(or `Max 8`), then restart Max or Live.

## The object

```
[polypitch~ -12]
```

| | |
|---|---|
| Inlets | signal left, signal right. Leave the right one unconnected for mono. |
| Outlets | signal left, signal right |
| `@semitones` | -12 to 12, default -12. Also the first argument. |
| `@mix` | 0 to 100. 0 = dry only, 50 = both at full level, 100 = shifted only (default). |
| `@tone` | 0 to 100. How much of the tone curve for the interval is applied to the shifted sound. Default 100. |
| `@response` | Shifting up only: 0 = fast (default, attacks about 8 ms late), 1 = balanced (about 12 ms, cleaner), 2 = clean (about 16 ms; the middle note of a full chord comes out right). |
| `clear` | Forget everything heard so far. |

The shifted sound is mono (the two inputs summed) and goes to both outlets. The dry signal passes in stereo and is
never delayed.

Changing `semitones` while audio runs restarts the engine's bands, which can click; so does changing `response`
while shifting up. That is on the roadmap.

## The Max for Live device

`max/device/Ben's Polyphonic Pitch Shifter.amxd` is `plugin~` into `polypitch~` into `plugout~`, with three dials (Semitones, Mix and
Tone) and a row of three buttons for Response (Fast, Balanced, Clean). It is generated by `max/tools/maxpatch.py`,
not drawn by hand, so that it can be rebuilt and reviewed as text. Like the rest of the device, the Response
buttons have not been seen or tried in Live yet.

The device is **not frozen**: it finds `polypitch~` through the installed package. That is fine on a machine where
the package is installed. To give the device to someone as a single file, open it in Max from Live (the edit
button on the device), press the Freeze button in the device's toolbar, and save; the object is then packed
inside. Freezing has to be redone whenever the object is rebuilt.

One thing to know about Max for Live in general: while a device is open in the Max editor, Live adds latency to
it. Close the editor before judging timing.

## Checking the object and the device inside Max

```
.venv/bin/python max/tools/check_in_max.py build     # writes build/maxcheck/: a test signal and a self-running patch
open -a Max build/maxcheck/check_<time>.maxpat       # about 25 seconds; the window closes itself
.venv/bin/python max/tools/check_in_max.py compare   # Max's recordings against the offline processor
```

The patch plays a test signal by sample index, with the output muted, through `polypitch~` at four settings and
through the device hosted by `amxd~` at three (one of them sets Response), and records each. `compare` nulls the recordings against
`build/tools/polypitch_cli` run at Max's sample rate and expects better than -100 dB.

The patch turns audio on for its own window and leaves Max's audio settings alone. **Do not run it while another
program is using the audio interface at a different sample rate**: starting Max's audio can switch the interface to
the rate in Max's settings.

## Building the object

```
C74_SDK=/path/to/max-sdk-base scripts/build.sh max
```

The source is one file, `max/PolyPitch/source/projects/polypitch_tilde/polypitch_tilde.cpp`, written against
Cycling '74's C API. A Windows build (`.mxe64`) should need only a Windows toolchain; it has not been tried.
